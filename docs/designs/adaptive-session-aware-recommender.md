## Problem Statement

This university Big Data & Storage project needs to demonstrate how long-term product preference and short-term session intent can work together in an e-commerce recommendation system. The repository is empty, so the first risk is not algorithm quality. It is failing to prove the complete storage, batch, streaming, serving, benchmarking, and recovery path within the four-week delivery window.

The project must use October REES46 events as historical training data, November events as chronological replay and evaluation data, and newly generated browser events as the live demo stream. The report must distinguish simulated replay from real live events and must not claim exactly-once behavior without recovery evidence.

## What Makes This Cool

The visible effect is simple and defensible: a user with long-term interest in computers can click several smartphones in one session and receive recommendations that shift toward smartphones without retraining ALS. The system demonstrates the change through a real event path rather than a static mock. The technical story underneath is the useful part: Spark learns the durable profile, Structured Streaming maintains recent session state, and the serving layer combines both signals.

## Constraints

- Four-week university milestone with three students and limited hardware.
- The project is primarily evaluated as a Big Data and Storage system, not as an SOTA recommendation model.
- October is training/history. November is held-out evaluation and replay. No temporal leakage.
- The original `product_id` remains the join key everywhere.
- ALS is offline. Live events update session state and re-ranking only.
- Invalid events go to a DLQ. Event IDs must be deterministic or stable across retries.
- Eventual consistency is acceptable. Exactly-once is a measured claim, not an assumption.
- Docker Compose comes before Kubernetes or a cloud-equivalent smoke deployment.
- The UI stays limited to catalog, product detail, cart, and recommendations.

## Premises

1. The course value is primarily the evidence of distributed storage and processing, not maximum recommendation accuracy.
2. October training, November replay/evaluation, and live demo events must remain separate so the results are temporally credible.
3. The team should validate the complete system boundary on tiny sample data before committing to full-data runs and benchmark targets.
4. Lambda Architecture remains the right baseline because the supplied project already separates batch history from replay/live speed processing, and a redesign would spend the four-week window without improving the evidence story.

## Approaches Considered

### Approach A: Batch-first vertical slice

Build October sample cleaning, implicit feedback, ALS, Top-N candidates, and a FastAPI response first. Add Kafka, Structured Streaming, Cassandra, and the browser later.

This is the fastest way to prove a recommendation result, but it delays the service-boundary tests that are most likely to cause integration rework.

### Approach B: Full Lambda vertical slice on tiny data

Connect the major boundaries early: October sample to Spark/ALS and Cassandra, November sample to Kafka and Structured Streaming, live events to session state, and FastAPI to the serving tables. Keep the React surface minimal until the backend path is stable.

This was selected because it tests the course-critical architecture early while keeping iteration fast through sample data.

### Approach C: Evidence-first headless pipeline

Prioritize Spark batch, Kafka replay, Structured Streaming, Cassandra, evaluation, latency, throughput, and recovery. Use only a thin API or CLI initially and defer most React work.

This maximizes course measurements but makes the live demo and user-facing event semantics late risks.

## Recommended Approach

Use Approach B. Start with a small, provenance-documented October sample and build the first complete path:

```text
October sample
  -> Spark validation and Silver Parquet
  -> implicit feedback and ALS
  -> Top-N candidate storage
  -> FastAPI recommendation response
```

Then connect the second path before polishing the UI:

```text
November replay or live click
  -> Kafka
  -> Spark Structured Streaming
  -> validation, deduplication, watermark, session intent
  -> Cassandra state
  -> FastAPI normalization and re-ranking
  -> minimal web refresh
```

The first coding milestone is not a full production stack. It is a reproducible sample run plus a working service boundary that proves the schema and candidate contract. Full-data execution, benchmarks, recovery, Kubernetes, monitoring, and UI polish follow only after that path works.

## Success Criteria

- A clean-environment command runs the October sample path and returns non-zero Top-K candidates.
- A known user can send an event through Kafka, Structured Streaming, Cassandra state, and FastAPI.
- A dominant session category changes the ranked recommendation output.
- Known-user, new-user-with-clicks, and completely new-user fallbacks work.
- November evaluation compares popularity, ALS, and ALS plus session-aware re-ranking.
- Spark evidence covers transformations, aggregations, joins, partition pruning, persistence, and AQE/skew discussion.
- Streaming evidence records input rate, processing rate, Kafka lag, P50/P95/P99 latency, watermark behavior, and checkpoint recovery.
- The report states what was measured, what was unavailable, and what exactly-once behavior was not proven.
